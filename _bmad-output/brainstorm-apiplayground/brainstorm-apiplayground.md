# ApiPlayground — intent

## Намерение

Создать развиваемый, работающий MVP веб-клиента для проверки HTTP API, похожего на упрощённый Postman. Основной сценарий должен быть понятным и быстрым: настроить запрос, отправить его, увидеть ответ, сохранить запрос и повторно использовать его. Интерфейс должен снижать лишние действия и не заставлять пользователя изучать сложные настройки; дополнительные возможности нужны только тогда, когда помогают работе с API.

## Пользователь и проблема

Начальная аудитория-гипотеза — разработчики, которые создают и отлаживают приложения и проверяют поведение API endpoints. Автор начинает с собственного опыта: при ошибке бывает трудно быстро определить, связана ли она с API, параметрами или форматом данных. Сейчас проверка может включать Swagger или Postman, ручную сверку запроса, а затем просмотр логов и отладку в IDE.

## Ценность и направление

ApiPlayground должен помогать быстро проверить endpoint и понять наблюдаемый результат, не добавляя сложности самому процессу. Контекст запроса и ответа важно сохранять вместе; диагностические подсказки и сравнение попыток могут помочь первичной проверке, но приложение не должно обещать достоверно определить причину, которую нельзя установить только по данным запроса и ответа. Отличие от Postman и Swagger пока является гипотезой: простота, понятность и низкая когнитивная нагрузка.

## Исходный объём MVP

- Методы GET, POST, PUT, PATCH и DELETE.
- Настройка URL, query-параметров, headers и JSON body.
- Просмотр HTTP status code, времени выполнения, response headers и body.
- История запросов, сохранённые запросы и коллекции.
- Безопасная отправка запросов с защитой от SSRF, таймаутами и ограничением размера ответа.

Технологический контекст: ASP.NET Core Web API / C#, React + TypeScript, PostgreSQL.

## Критерии успеха

- Пользователь может без долгого освоения интерфейса настроить, отправить и проверить HTTP-запрос.
- Запрос можно сохранить и повторно использовать; основные детали ответа легко найти.
- MVP является работающим и имеет понятную структуру, пригодную для развития, а не только демонстрирует идею.
- Автор на практике проходит путь BMAD от идеи до работающего MVP и учится самостоятельно организовывать этот процесс.

## Что ещё проверить

- Для каких разработчиков и сценариев простота ApiPlayground даст заметное преимущество перед Swagger или Postman.
- Какие диагностические подсказки действительно помогают, не создавая ложной уверенности о причине ошибки.
- Где провести границу между необходимыми возможностями MVP и функциями, перегружающими основной сценарий.
