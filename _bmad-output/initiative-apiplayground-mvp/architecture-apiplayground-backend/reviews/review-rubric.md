# Independent Good-Spine Review — ApiPlayground Backend

**Verdict: Needs revision before handoff.** The spine is a useful, capability-traceable target architecture and reconciles several important constraints, especially the safety-first sequencing, local-only runtime, preservation of migration history, and separation of transport outcomes. However, its required architecture-boundary migration is not present in the approved epic ticket sequence; local API security is left to a consequentially open implementation choice; and the single guarded outbound path is not specified with enough verification to demonstrate it cannot be bypassed or multiply implemented. The pinned EF/Npgsql package versions are also already behind current servicing releases. These are material for a high-risk outbound-request MVP.

## Scope and review basis

Reviewed the spine against the BMAD good-spine checklist in `reviewer-gate.md`, the complete listed initiative/spec/epic/ticket/story-plan sources, the UX experience constraints where they bear on backend ownership, and the brownfield repository baseline (`README.md`, project/solution files, API startup, launch settings, CI, and current migration). This was an independent document review; the spine was not edited. The reviewer gate's checklist asks whether the spine resolves lower-level divergence points, has enforceable rules, covers altitude-owned dimensions, reconciles sources/brownfield reality, and safely bounds Deferred.

The spine covers CAP-1–CAP-4 and the spec's five methods, request inputs, response fields, replay, persistence across sessions, and mandatory outbound protections. Its mappings and AD-1–AD-6 give a strong ownership baseline. Current source evidence includes [spec-apiplayground.md](../spec-apiplayground/spec-apiplayground.md), [mvp-scope.md](../spec-apiplayground/mvp-scope.md), [initiative-apiplayground-mvp.md](../initiative-apiplayground-mvp.md), [epic-apiplayground-mvp.md](../epic-apiplayground-mvp/epic-apiplayground-mvp.md), [tickets.toml](../epic-apiplayground-mvp/tickets.toml), [story-local-platform-baseline-plan.md](../epic-apiplayground-mvp/story-local-platform-baseline-plan.md), [EXPERIENCE.md](../ux-apiplayground/EXPERIENCE.md), and the repository's [README.md](../../../README.md), [Program.cs](../../../backend/src/ApiPlayground.Api/Program.cs), [ApiPlayground.Api.csproj](../../../backend/src/ApiPlayground.Api/ApiPlayground.Api.csproj), [launchSettings.json](../../../backend/src/ApiPlayground.Api/Properties/launchSettings.json), and [ci.yml](../../../.github/workflows/ci.yml).

## Findings

### High — The required architecture-boundary story is absent from the approved epic

**Evidence:** The spine's Design Paradigm and Deferred require a dedicated architecture-boundary story after Story 1 and before Story 2 to create four projects, move the context/migration, update references/CI, and add boundary checks ([architecture spine](../architecture-apiplayground-backend.md#L27), [architecture spine](../architecture-apiplayground-backend.md#L129)). The canonical [tickets.toml](../epic-apiplayground-mvp/tickets.toml) defines Story 2 as Outbound request safety foundation, with `after = [1]`, and contains no architecture-boundary story. The baseline story plan says Story 1's current single-project API and migration are the accepted baseline ([baseline plan](../epic-apiplayground-mvp/story-local-platform-baseline-plan.md#L31), [baseline plan](../epic-apiplayground-mvp/story-local-platform-baseline-plan.md#L67)); the actual [solution](../../../backend/ApiPlayground.sln) contains only Api and Tests, and [Program.cs](../../../backend/src/ApiPlayground.Api/Program.cs#L1-L10) registers the DbContext directly in Api.

**Why it matters:** The spine has made a required sequencing/ownership decision that no approved ticket schedules or verifies. Story 2 may proceed after Story 1 under the current graph without the four-project boundary, while the spine claims the boundary must precede it. This is a direct handoff divergence, not merely a future implementation detail.

**Disposition:** Discuss/update the epic ticket set and dependency graph to add an explicit migration story (including migration identity/history and automated checks), or revise the spine to assign that work to an existing approved ticket and update its acceptance criteria. Do not treat the current wording as scheduled work.

### High — Local API origin protections are deferred without a constrained secure outcome

**Evidence:** AD-6 requires local-only binding/exposure but defers host binding, browser-origin mechanism, and protections against unintended cross-origin invocation until before UI dispatch ([architecture spine](../architecture-apiplayground-backend.md#L74-L78), [architecture spine](../architecture-apiplayground-backend.md#L133)). It also says not to expose the unauthenticated request-triggering API to the local network by default. The API is intentionally unauthenticated in the current scaffold: [Program.cs](../../../backend/src/ApiPlayground.Api/Program.cs#L1-L10). The developer launch profile binds localhost ([launchSettings.json](../../../backend/src/ApiPlayground.Api/Properties/launchSettings.json#L1-L12)), while the README starts with `--urls http://localhost:5000`; this is useful current evidence but not an invariant on every future launch path. The UX experience also identifies local-origin protections as unresolved ([EXPERIENCE.md](../ux-apiplayground/EXPERIENCE.md#L113-L120)).

**Why it matters:** A reverse proxy versus permissive CORS, an origin check, host validation, authentication, and loopback binding do not provide equivalent security properties. The current Deferred text names the problem but does not state acceptable controls, reject unsafe alternatives, assign the decision to a story, or require verification. A developer can satisfy “local-only” in a way that still permits a hostile local webpage to invoke the request-triggering endpoint, or accidentally bind it to a LAN interface. This is especially significant because the API is an SSRF-capable deputy once dispatch exists.

**Disposition:** Discuss and resolve before Story 3/UI dispatch. Require loopback-only binding for the local profile and make the chosen browser/API protections explicit and testable; treat CORS alone as a browser policy, not proof of API authorization. Tie the decision and tests to the API-origin story/acceptance criteria. Preserve the explicit prohibition on default LAN exposure.

### High — AD-4's “single guarded path” needs stronger enforceability and proof criteria

**Evidence:** AD-4 says all dispatch uses one Application port and a single guarded Infrastructure implementation, but says it does not select policy values ([architecture spine](../architecture-apiplayground-backend.md#L62-L66)). AD-5 promises automated checks for forbidden project references and direct target HTTP dispatch outside the guarded adapter, plus a separate Story 9 suite ([architecture spine](../architecture-apiplayground-backend.md#L68-L72)). The approved Story 2 ticket requires allow/deny, DNS/rebinding, redirect, timeout, and response-size tests after owner approval ([tickets.toml](../epic-apiplayground-mvp/tickets.toml#L16-L27)); the spec mandates SSRF protection, timeout enforcement, and response-size limits but deliberately leaves policies and thresholds open ([spec-apiplayground.md](../spec-apiplayground/spec-apiplayground.md#L33-L36)).

**Why it matters:** “No direct HTTP dispatch outside adapter” can catch obvious bypasses but does not itself establish that every outbound path resolves to the guarded policy implementation, that redirects/retries cannot escape it, that dependency injection cannot register an alternate adapter, or that the policy actually approved is the one exercised by independent tests. The spine says only the port/adapter cardinality in prose and does not name a fail-closed behavior for missing/ambiguous guard configuration. The owner approval gate is present in source tickets, but the architecture leaves no durable policy/approval artifact or explicit link between approved values, runtime configuration, and test cases. As written, implementations with materially different enforcement can both claim conformance.

**Disposition:** Tighten AD-4/AD-5 and the Story 2/9 verification criteria: make guard registration singular/fail-closed; prohibit alternate outbound transports in runtime code (including redirects/handler paths); require tests to prove the configured approved policy and all mandatory cases; and make the owner-approved policy/test-target record a prerequisite artifact. Keep thresholds deferred until approved, but require their explicit resolution before any dispatch as already intended.

### Medium — Current stack pins lag servicing updates

**Evidence:** The spine records EF Core Design 10.0.0 and Npgsql EF provider 10.0.0 as project-pinned/build-verified ([architecture spine](../architecture-apiplayground-backend.md#L80-L87)); the current [ApiPlayground.Api.csproj](../../../backend/src/ApiPlayground.Api/ApiPlayground.Api.csproj#L4-L15) confirms both are pinned at 10.0.0. As of the review date (2026-10-19), NuGet lists Microsoft.EntityFrameworkCore.Design 10.0.13 and Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3 as current package versions ([NuGet EF Design](https://www.nuget.org/packages/Microsoft.EntityFrameworkCore.Design), [NuGet Npgsql provider](https://www.nuget.org/packages/Npgsql.EntityFrameworkCore.PostgreSQL)); Microsoft's support policy requires remaining current on servicing patches ([.NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)).

**Why it matters:** “Build-verified” proves compatibility at the old pinned version, not current servicing. The stack table's currency claim is stale for both packages and can propagate an unnecessary patch/security lag into the architecture-boundary migration.

**Disposition:** Update compatible pins and verify the solution, or qualify the stack as a known temporary baseline with an explicit patch-servicing update gate before the next implementation. The PostgreSQL 17 major/minor statement is current: PostgreSQL lists 17.11 as supported and recommends the current minor ([PostgreSQL versioning](https://www.postgresql.org/support/versioning/)). .NET 10 is LTS, but the local SDK value is correctly labeled observed and not repository-pinned.

### Medium — Local data lifecycle and operational ownership are omitted or under-owned

**Evidence:** The backend spine assigns local PostgreSQL, connection configuration, CI database provisioning, and migration ownership, and defers the CI/local test-service mechanism ([architecture spine](../architecture-apiplayground-backend.md#L74-L78), [architecture spine](../architecture-apiplayground-backend.md#L129-L134)). The UX source explicitly leaves History retention/limits and local-data lifecycle (including reset/deletion behavior) open ([EXPERIENCE.md](../ux-apiplayground/EXPERIENCE.md#L113-L120)). The epic says environments, CI, deployment, and operations belong to opening stories ([epic-apiplayground-mvp.md](../epic-apiplayground-mvp/epic-apiplayground-mvp.md#L27-L31)), but the existing baseline ticket only establishes local startup, migrations, CI, and harness readiness ([tickets.toml](../epic-apiplayground-mvp/tickets.toml#L5-L9)); current CI builds/tests without a PostgreSQL service ([ci.yml](../../../.github/workflows/ci.yml#L1-L32)).

**Why it matters:** Data retention and deletion affect what the product stores locally and for how long; they are not only schema details. CI provisioning is acknowledged but has no ticket owner or acceptance check yet. Basic operational expectations—how migration ownership/roll-forward is controlled, and how startup/database failure is detected—are not decided or explicitly deferred to an owner. These gaps can yield incompatible retention and operational behaviors while still satisfying the structural rules.

**Disposition:** Defer the user-facing retention/reset policy to the History/Collections story or owner decision, with a no-unbounded-retention assumption avoided until approved. Explicitly assign CI PostgreSQL provisioning and migration/startup health behavior to the platform/boundary story and test it. No public deployment, backup service, or external observability stack is implied by this review; those remain outside the local MVP unless an owner decision expands scope.

## Deferred safety assessment

Deferred is mostly well structured: exact SSRF/redirect/timeout/size policies and sensitive-header classification are explicit owner decisions with “must be settled before” guards; contract details and data shapes are bounded by named stories and canonical acceptance criteria; frontend internals are correctly outside this backend spine. Those items can remain deferred without licensing arbitrary implementations **if** their stated gates are preserved.

Three exceptions need closure: (1) the architecture-boundary migration has no scheduled ticket; (2) local-origin protection options are named but not constrained to secure/testable outcomes; and (3) the approved outbound policy has no specified artifact/trace from approval to production configuration and independent tests. CI PostgreSQL provisioning and data lifecycle are acknowledged but weakly assigned. These leave materially different implementations possible, so they are not safe “story-level detail” as currently written.

## Checklist disposition

- **Divergence coverage:** Good mapping for CAP-1–CAP-4 and cross-cutting testing/local topology; missing migration-story handoff and local-origin/security enforcement details.
- **Enforceability:** AD-1/AD-3/AD-5 provide useful project and technology boundaries, but no approved ticket currently installs the boundary checks; AD-4 needs fail-closed/cardinality and policy-to-test proof criteria.
- **Altitude-owned dimensions:** Backend ownership, persistence, outbound transport, and local topology are addressed. Data retention/lifecycle and CI/operational startup-health ownership are not adequately closed or assigned.
- **Source reconciliation:** Most product and safety constraints are faithfully carried forward. The dedicated architecture story conflicts with the actual epic plan (`Story 2 after Story 1`); stack package pins no longer support the implied currentness.
- **Deferred:** Most policy/value and story-detail deferrals are appropriately gated. Local-origin protections, missing migration schedule, and the policy approval/configuration/test chain leave incompatible outcomes possible.
