- (note) Guided distillation selected. Source: ../../brainstorm-apiplayground/brainstorm-apiplayground.md. Preserve source uncertainty; do not convert audience/differentiation hypotheses to facts.
- (decision) Why: ApiPlayground aims to make routine API verification straightforward for developers who want a lighter alternative to complex interfaces/settings: configure and send an HTTP request, inspect the response, and save requests for reuse without unnecessary features. Developer audience and comparative advantage remain hypotheses from the source, not validated market facts.
- (capability) CAP-1 intent confirmed: configure and send HTTP requests using the MVP-supported methods and request fields. Success criterion not yet confirmed; elicit before rendering.
- (capability) CAP-2 intent confirmed: inspect the HTTP response. Success criterion not yet confirmed; elicit before rendering.
- (capability) CAP-3 intent confirmed: review request history and repeat a prior request. Success criterion not yet confirmed; elicit before rendering.
- (capability) CAP-4 intent confirmed: save requests and organize them in collections for reuse. Success criterion not yet confirmed; elicit before rendering.
- (capability) CAP-1 success confirmed: a user can select GET/POST/PUT/PATCH/DELETE, set URL and applicable query parameters, headers, and JSON body, then send a request whose method and values match the selection.
- (capability) CAP-2 success confirmed: after an endpoint responds, the user can inspect its HTTP status, elapsed time, response headers, and response body.
- (capability) CAP-3 success confirmed: a sent request appears in history; the user can select it and resend with the same method, URL, parameters, headers, and body.
- (capability) CAP-4 success confirmed: a user can save a request into a collection, find it later, and reuse it; saved requests remain available in a later work session.
- (constraint) MVP outbound HTTP requests must include protections against SSRF, enforce timeouts, and limit response size. Specific SSRF policy and timeout/size thresholds remain unresolved.
- (note) Implementation context from approved source: ASP.NET Core Web API/C#, React + TypeScript, PostgreSQL. Keep in stack.md companion rather than prescribing implementation in the spec kernel.
- (decision) Non-goal confirmed: MVP will not promise automatic, definitive identification of every error's true cause. It will display HTTP status, headers, response body, and other available diagnostic information; causal claims must be limited to what request/response evidence supports.
- (event) Success signal confirmed: demonstrate configure/send HTTP request, inspect response, find history entry, and reuse saved collection request in a later session; independently verify outbound-request safety protections with tests. Do not add time targets or subjective usability metrics.
